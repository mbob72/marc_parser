# Политика импорта РГБ от 22.09.2026

Решение владельца требований применяется к конвертации ISO 2709 и Aleph
sequential в MARC-JSON, включая CLI, worker и диагностический аудит.

## Порядок обработки

1. Прочитать границы записи и полей. В Aleph это префикс и байтовые длины;
   в ISO — структурные позиции Leader, Directory и разделители.
2. Найти поле `DEL` с подполем `a`, значение которого **точно** равно `Y`.
   Достаточно одного совпадения среди повторных полей или подполей. Всю запись
   пропустить до проверки содержимого Leader, индикаторов и подполей.
3. В оставшихся записях убрать поля с тегом из трёх ASCII-букв, независимо
   от регистра: `LKR`, `DEL`, `OWN`, `UID` и другие. Их содержимое и маркер
   Aleph-поля не проверять. Смешанный буквенно-цифровой тег, например `A1B`,
   этим правилом не исключается и проходит обычную проверку DR-E2.
4. Исключения: Aleph `LDR` становится `leader`, `FMT` становится `format`.
   В ISO источник `leader` — 24-байтовый заголовок записи. Внутренняя модель
   сохраняет FMT для проверки формата; в JSON `fields` ни LDR, ни FMT нет.
5. Пересчитать длину записи и адрес данных после исключения полей,
   проверить оставшуюся MARC-модель и записать JSON и ошибки валидации.

Теги DEL/LDR/FMT распознаются без учёта регистра. Код подполя `a` и значение
`Y` сравниваются с учётом регистра, без удаления пробелов. `a=y`, `A=Y`,
`a=YY` и `a=Y ` не означают удаление. В Aleph проверяется `$$aY`, в ISO —
разделитель `0x1F`, код `a` и значение `Y` до следующего разделителя или
конца поля. Поиск простого вхождения текста `DEL`/`Y` в записи не используется.

Удалённые записи не вызывают MARC-валидатор, не попадают в JSON и отчёт
валидации. В Aleph у них допустимы отсутствующий, повторный или короткий
LDR и неподдерживаемый маркер другого поля: эти проверки уже не выполняются.
Повреждение границ контейнера остаётся структурной ошибкой: без надёжного
выделения полей нельзя установить принадлежность DEL текущей записи.

## Leader и format

К ранее допустимым значениям Leader/19 добавлены `a`, `b`, `c`.
Они сохраняются и больше не вызывают LD-02; новый закрытый список значений
не вводится. Проверка Leader/18 на `c` и `n` сохранена.
[История решения и противоречие страниц 19/33](RSL-Leader-19-conflict.md).

Проверка содержимого LDR и FMT остаётся. Например, LDR неправильной длины
у неудалённой Aleph-записи вызывает ошибку парсинга, неизвестный FMT — ошибку
валидации FMT. При отсутствии FMT по прежнему контракту `format` равен `""`;
новое требование обязательного FMT не вводится.

## Статистика и локализация

`skippedDeletedRecords` — число записей, исключённых по DEL. Оно входит в
статистику конвертера, итоговый лог CLI, summary задания worker/API и новые
strict/diagnostic-сводки аудита. Пропуски не относятся к `validRecords`,
`recordsWithValidationErrors` или `recordsWithParsingErrors`.

Для успешно завершённой обычной конвертации:

```text
recordsProcessed = validRecords + recordsWithValidationErrors + skippedDeletedRecords
строк JSON = validRecords + recordsWithValidationErrors
```

`recordIndex` и `byteOffset` относятся к исходному файлу и учитывают пропуски.
Номер строки JSON после пропусков не равен `recordIndex + 1`.
`fieldIndex` в новых ошибках относится к отфильтрованной внутренней модели,
где FMT присутствует; это не индекс поля в исходной строке и не индекс JSON
`fields`. Для поиска используйте также тег и исходное смещение записи.
Файл только из удалённых записей даёт пустой JSON без отчёта валидации.

## Реализация и история

Конвейер импорта вызывает `parseForImport()`: результат `null` означает
удалённую запись. Низкоуровневый `parse()` сохранён для разбора исходной модели
и проверки обратной сериализации; он не применяет политику отбора.
Обратное направление JSON → ISO/Aleph сериализует предоставленные данные;
уже исключённые поля и записи восстановить из JSON нельзя. Отдельный атрибут
для сохранения служебных полей не добавляется.

Артефакты прогона 17.09.2026 остаются историческими. Их количества и списки
ошибок не пересчитываются по новым правилам; новый аудит следует запускать
в отдельную директорию. Описание VF-G5 сохранено как deprecated в документации
и её генераторах для чтения старых выкладок. В исполняемом валидаторе и его
типах этого кода нет: недопустимый код подполя даёт только SF-G4.
