# Алгоритм двусторонней конвертации MARC РГБ

Документ фиксирует реализованный контракт
`ISO 2709/Aleph sequential ↔ MARC-JSON`, формат многострочного
файла, обработку служебного `FMT`, пересчёт Leader и работу асинхронного
сервиса.

Номера страниц ниже — физические номера страниц файла
`DevRGB-170826-1001-43.pdf` (208 страниц), а не номера разделов документа.

## Основание профиля РГБ

На стр. 17–19 PDF описана схема MARC-JSON РГБ:

- перечислены стандартные поля, которые в РГБ не используются (стр. 17);
- перечислены отсутствующие в профиле подполя (стр. 18–19);
- указаны ограничения Leader/18 и Leader/19 (стр. 19); для импорта
  проектом принято уточнение от 22.09.2026: Leader/19 `a`, `b`, `c` допустимы;
- описаны добавленные метаданные полей `label`, `url_rsl`, `url_loc`,
  `repeatable`, `active_rsl`, `required` и метаданные подполей `label`,
  `required`, `repeatable`, `subfield_type`, `depends_on`, `default`
  (стр. 19).

Эти атрибуты относятся к схеме/модели редактора, а не к экземпляру записи.
Поэтому конвертер не добавляет их в каждый объект MARC-JSON: экземпляр
содержит `leader`, `format`, `fields` и, только для Aleph, `recordId`, а
метаданные остаются в целевой схеме РГБ.

Структурная модель ISO 2709 взята из стр. 30 PDF: 24-байтовый Leader,
12-байтовые статьи Directory, разделитель поля `0x1E`, разделитель подполя
`0x1F` и разделитель записи `0x1D`.

## Файловый контракт MARC-JSON

Выход в JSON является NDJSON (newline-delimited JSON):

```text
{"leader":"...","format":"BK","fields":[...]}
{"leader":"...","format":"CR","fields":[...]}
```

Правила:

1. Одна MARC-запись представлена одним компактным JSON-объектом.
2. После каждого объекта, включая последний, записывается `LF`.
3. Несколько объектов не оборачиваются в JSON-массив и не разделяются
   запятыми.
4. Пустой ISO-файл даёт пустой JSON-файл.
5. Обратное направление читает одну запись на непустую строку; пустые строки
   пропускаются. Многострочный pretty-printed объект и JSON-массив входным
   контрактом не являются.
6. Имя результата содержит источник: `.iso.json` или `.aleph.json`.
   Обратный конвертер не принимает JSON без одного из этих маркеров.
7. Aleph-запись дополнительно содержит верхнеуровневый `recordId` — ровно
   девять цифр из первой колонки Z00. Для ISO это свойство отсутствует.

Такой формат позволяет обрабатывать большие файлы потоково и локализовать
ошибку обратного преобразования номером строки.

## Автоопределение входного формата

Направление `--to-json` и соответствующее направление сервиса принимают два
байтовых формата. Если первые десять байтов совпадают с шаблоном
`ddddddddd<TAB>`, выбирается Aleph sequential; иначе используется ISO 2709.
Расширение файла на выбор алгоритма не влияет. Можно также явно передать ядру
`inputFormat: "iso2709"` или `inputFormat: "aleph-sequential"`.

Строковый контейнер Aleph sequential найден в предоставленных реальных
выгрузках `rsl06_z00.dat`, `rsl07_z00.dat` и `rsl10_z00.dat`. Сам контейнер не
описан в PDF; PDF используется для интерпретации его MARC-полей: структура
MARC — стр. 30, служебное поле `FMT` — стр. 84. Поэтому ниже отдельно указаны
правила, подтверждённые файлами, и правила, взятые из PDF.

## ISO 2709 / Aleph sequential → MARC-JSON

### 1. Разделение потока на записи

Конвертер читает первые пять ASCII-байтов очередной записи как объявленную
длину. Он ждёт полного количества байтов, проверяет фактическую длину и
конечный `0x1D`, затем передаёт одну запись парсеру. Незавершённая запись или
некорректная длина считаются фатальной ошибкой файла.

Для Aleph sequential логическая запись имеет форму:

```text
NNNNNNNNN<TAB>{LLLLTTTIILvalue}...<LF>
```

где `NNNNNNNNN` — номер записи; `LLLL` — четыре ASCII-цифры длины следующего
поля в байтах; `TTT` — тег; `II` — два индикатора; `L` — маркер поля; `value`
— данные. Длина включает `TTTIILvalue`, но не собственные четыре цифры.
Допустим и разделитель записи `CRLF`.

Фреймер не ищет ближайший перевод строки вслепую. Он сначала пропускает ровно
`LLLL` байтов каждого поля и признаёт `LF`/`CRLF` границей только в позиции
между завершёнными полями. Поэтому обычный `LF` или Unicode line separator
`U+2028` внутри значения не разрывает запись. Длина считается по исходным
байтам, а не по числу Unicode-символов; это существенно для кириллицы UTF-8.
Незавершённое поле, неверный префикс или нечисловая длина являются фатальной
ошибкой framing, как и для ISO 2709.

### 1а. Отбор перед валидацией

После чтения границ полей проверяется `DEL$a=Y`. Такая запись пропускается
целиком, без проверки содержимого Leader и остальных полей, без JSON и ошибок
валидации; увеличивается `skippedDeletedRecords`.
У остальных записей исключаются буквенные поля, кроме LDR/FMT: они становятся
атрибутами `leader`/`format`. Их содержимое продолжает проверяться.
Для ISO расположение DEL требует структурно читаемых Leader и Directory;
повреждённые границы нельзя игнорировать. Полный контракт и статистика:
[политика импорта](RSL-import-policy.md).

### 2. Leader и Directory

Из первых 24 байтов извлекается Leader. Leader/12–16 задаёт базовый адрес
области данных, а Leader/20–22 — размеры частей статьи Directory. Для обычной
карты `4500` статья имеет вид:

```text
TTTLLLLPPPPP
```

где `TTT` — тег, `LLLL` — длина поля вместе с `0x1E`, `PPPPP` — смещение от
базового адреса. Это соответствует описанию на стр. 30 и порядку формирования
Leader на стр. 32–34 PDF.

В Aleph sequential отдельное поле `LDR` преобразуется в 24-байтовый Leader.
Символ `^`, которым выгрузка обозначает пробел, нормализуется в ASCII SPACE.
Для передачи записи общему парсеру пересчитываются структурные позиции
Leader/00–04, Leader/12–16 и Leader/20–23; остальные позиции сохраняются.
Таким образом, дальнейшие валидация и JSON-сериализация общие для обоих
входных контейнеров.

### 3. Поля и подполя

- `00X` разбираются как контрольные поля без индикаторов и подполей;
- `FMT` разбирается как служебное контрольное поле РГБ/Aleph;
- остальные поля содержат два индикатора и последовательность подполей,
  начинающихся с `0x1F` и однобайтового кода;
- значения декодируются кодировкой задания (`utf-8`, `windows-1251` и т. п.).

Для Aleph sequential `$$` преобразуется в байт-разделитель подполя `0x1F`, а
`^` в индикаторах и контрольных полях — в пробел. Девятизначный номер до
табуляции записывается в `recordId` и не создаёт новое поле `001`: поле `001`
берётся только из самой MARC-записи.

Описание контрольных полей и полей данных также дано на стр. 30 PDF.

### 4. Определение `format`

На стр. 84 PDF `FMT` назван служебным полем Aleph, содержащим формат
библиографической записи. Поэтому алгоритм:

1. находит `FMT`;
2. помещает исходное значение в верхнеуровневый `format`;
3. исключает `FMT` из `fields`.

Стр. 28–29 PDF описывают стандартную зависимость формата MARC 21 от
Leader/06 и Leader/07. Она не используется как fallback профиля РГБ, потому
что назначенный в Aleph `FMT` является отдельным источником данных. При
отсутствии `FMT` возвращается пустая строка.

### 5. Ошибки

Структурная ошибка прерывает обработку исключением. Ошибки валидации
сохраняются в отдельном отчёте `*.validation-errors.ndjson` после завершения
парсинга. Значения не заменяются; обработка следующих записей продолжается.

Фатальная ошибка framing не публикует частичный результат. Запись сначала
идёт во временный файл и атомарно переименовывается только после успешного
завершения потока.

## MARC-JSON → исходный контейнер

Контейнер выбирается только по имени входного JSON:

| Суффикс JSON | Результат |
| --- | --- |
| `.iso.json` или `.iso.ndjson` | ISO 2709 (`.mrc`) |
| `.aleph.json` или `.aleph.ndjson` | Aleph sequential (`.dat`) |

Немаркированное имя отклоняется до начала записи результата. Старые JSON без
маркера не поддерживаются намеренно: это исключает неоднозначность и не требует
добавлять в каждую запись тяжёлую копию исходных байтов.

### 1. Проверка JSON-записи

Для каждой непустой строки проверяется структура JSON, длина Leader (24
ASCII-байта), длина тега (3 ASCII-байта), длина индикатора и кода подполя
(1 ASCII-байт), типы значений и отсутствие смешанных свойств поля.
Структурные нарушения и невозможность закодировать значение без потерь
прерывают преобразование.

Ограничения профиля на FMT, Leader/18, теги, индикаторы и коды подполей
проверяются общим валидатором после сериализации. Неизвестные значения
и пустые массивы подполей сохраняются. Ошибки записываются в отдельный
отчёт по завершении потока; обработка продолжается.

Для Aleph дополнительно требуется девятизначный `recordId`. Для вручную
созданного JSON допускается числовое поле `001` длиной до девяти цифр как
fallback; оно дополняется нулями слева.

Смешанные поля отклоняются, а не обрабатываются с потерей запрещённых
свойств. Общая проверка вызывается через `MarcIsoSerializer` для обоих
выходных контейнеров. Разделение TypeScript-контракта и runtime-проверки
описано в [контракте типов](./Контракт%20типов%20ядра%20трансформации%20MARC.md#typescript-и-runtime-валидация-через-zod).

Символ `#` в индикаторе преобразуется в ASCII-пробел. В PDF `#` используется
как экранное обозначение пробела (стр. 30 и 39), тогда как в данных хранится
пробел.

### 2. Кодирование ISO 2709

Текст кодируется указанной кодировкой. Для каждого поля строится байтовое
представление:

- `FMT`: код `format` + `0x1E`;
- контрольное поле: закодированное `value` + `0x1E`;
- поле данных: `ind1`, `ind2`, затем для каждого подполя `0x1F`, код и
  закодированное значение, в конце `0x1E`.

После кодирования выполняется обратная проверка значения. Если выбранная
кодировка не может представить хотя бы один символ, запись отклоняется вместо
молча́ливой замены символа знаком `?`.

Длина поля ограничена четырьмя цифрами Directory, то есть 9999 байт.

### 3. Directory

`FMT` создаётся первым, после него в исходном порядке идут элементы `fields`.
Для каждого поля рассчитываются:

- четырёхзначная длина, включающая `0x1E`;
- пятизначное смещение от начала области полей.

После последней 12-байтовой статьи записывается `0x1E`. Правила соответствуют
стр. 30 PDF.

### 4. Пересчёт Leader

Система всегда пересчитывает:

- Leader/00–04 — полную длину записи, включая финальный `0x1D`;
- Leader/12–16 — `24 + 12 × число_полей + 1`;
- Leader/20–23 — `4500` для четырёхзначной длины и пятизначного смещения.

Пересчитываемые позиции описаны на стр. 32–34 PDF. Остальные позиции исходной
строки Leader сохраняются. Максимальная длина записи — 99999 байт.

После Leader, Directory и полей записывается `0x1D`.

### 5. Кодирование Aleph sequential

Сериализатор записывает `recordId`, табуляцию, затем `FMT`, `LDR` и остальные
поля. Для каждого поля заново вычисляется четырёхзначная байтовая длина.
Подполя кодируются как `$$<код><значение>`, пробелы в Leader и контрольных
полях — как `^`, запись завершается `LF`. Значения кодируются выбранной
кодировкой с той же проверкой невозможных символов, что и ISO.

Получается каноническое Aleph-представление: гарантируется сохранение
`recordId` и MARC-данных, оставшихся после отбора при импорте, но не побайтовое совпадение служебной записи с
исходником. В частности, длины пересчитываются, а пробелы нормализуются в `^`.
Гарантируемый инвариант имеет вид
`Aleph → JSON₁ → Aleph → JSON₂`, где `JSON₁ = JSON₂` для корректных записей.

### 6. Атомарность

Весь результат сначала пишется во временный файл. Ошибка JSON или модели
содержит номер строки, удаляет временный файл и не заменяет ранее существующий
результат. После успешной обработки временный файл атомарно переименовывается
в `.mrc` или `.dat`.

## CLI

По умолчанию используется направление ISO/Aleph sequential → JSON с
автоопределением контейнера и обязательным маркером в результате:

```bash
marc-parser records.mrc records.json utf-8
marc-parser records.mrc records.json windows-1251 --to-json
marc-parser rsl06_z00.dat rsl06.json utf-8
```

Фактические имена результатов: `records.iso.json` и `rsl06.aleph.json`.

Обратное направление:

```bash
marc-parser records.iso.json records.mrc utf-8 --to-iso
marc-parser rsl06.aleph.json rsl06.dat utf-8 --to-iso
```

Выходное расширение в обратном направлении выбирается по маркеру: `.mrc` или
`.dat`. Переданное несовместимое расширение заменяется.

## API, очередь и worker

`POST /jobs` принимает multipart-поля:

- `file` — один входной файл;
- `encoding` — кодировка данных MARC;
- `direction` — `iso-to-json` (по умолчанию) или `json-to-iso`;
- `format` — контейнер прямого входа: `aleph-sequential` (по умолчанию) или
  `iso2709`.

Имя направления `iso-to-json` охватывает оба исходных контейнера, но сервис
не полагается на эвристику: worker читает `conversion_jobs.input_format` и
возвращает `.aleph.json` либо `.iso.json`. Таким образом, актуальный формат
выгрузок РГБ Aleph sequential является явным default; для ISO клиент передаёт
`format=iso2709`. CLI при прямой конвертации по-прежнему умеет автоопределение.
Направление `json-to-iso` сохранено в API, но фактический контейнер выбирается
по маркеру имени загруженного JSON.

Пример обратного задания:

```bash
curl -F file=@records.iso.json \
  -F encoding=utf-8 \
  -F direction=json-to-iso \
  http://localhost:3000/jobs
```

Направление и контейнер сохраняются в `conversion_jobs.direction` и
`conversion_jobs.input_format`. В RabbitMQ по-прежнему передаются только
`jobId` и номер попытки; worker читает параметры из PostgreSQL и запускает тот
же конвертер, что использует CLI.

Результаты:

| Направление | Расширение | MIME |
| --- | --- | --- |
| `iso-to-json`, вход ISO | `.iso.json` | `application/x-ndjson; charset=utf-8` |
| `iso-to-json`, вход Aleph | `.aleph.json` | `application/x-ndjson; charset=utf-8` |
| `json-to-iso`, имя `.iso.json` | `.mrc` | `application/marc` |
| `json-to-iso`, имя `.aleph.json` | `.dat` | `application/octet-stream` |

Повторные попытки, dead-letter queue и статусы задания одинаковы для обоих
направлений.

## Проверяемые инварианты

Автотесты проверяют:

- два входных ISO-record дают две строки NDJSON;
- два объекта NDJSON дают две последовательные ISO-записи;
- `ISO → .iso.json → ISO → .iso.json` сохраняет MARC-модель;
- `Aleph → .aleph.json → Aleph → .aleph.json` сохраняет `recordId` и
  MARC-модель;
- Leader/00–04 и Leader/12–16 совпадают с фактически построенной записью;
- `FMT` присутствует в ISO и не дублируется в JSON `fields`;
- Windows-1251 проходит круговое преобразование;
- ошибка второй строки не перезаписывает существующий результат;
- worker выполняет оба направления и публикует результат с нужным
  расширением.

Дополнительно зафиксированы три небольших фрагмента реальных данных: по одной
записи `rsl06/BK`, `rsl07/SE` и `rsl10/AU`. Тесты проверяют полный круг через
`.aleph.json`, `recordId`, кириллицу, нормативную запись, `FMT` и framing при
переводе строки внутри значения.

## Полная проверка реальных выгрузок

Архив из предоставленной ссылки проверен с SHA-256
`7c9f56b725e421d45437af901c627d003a1a64880cc035fd5af60021fd62444d`.
Потоковый прогон не загружал файлы целиком в память и обработал все записи:

| Файл | Записей | Корректных | С ошибками валидации | С ошибками парсинга |
| --- | ---: | ---: | ---: | ---: |
| `rsl06_z00.dat` | 101 991 | 101 885 | 106 | 0 |
| `rsl07_z00.dat` | 525 689 | 525 679 | 9 | 1 |
| `rsl10_z00.dat` | 273 151 | 273 118 | 28 | 5 |
| **Итого** | **900 831** | **900 682** | **143** | **6** |

Все три потока завершились без фатальной ошибки framing и прочитали точное
число входных байтов. Шесть локальных ошибок находятся в исходных данных:
одна запись `rsl07` без `LDR`; четыре записи `rsl10` имеют 25 байтов в `LDR`
из-за кириллической `т` вместо однобайтового ASCII-кода; одна запись `rsl10`
содержит два `LDR`. В прежней реализации для этих записей создавались заглушки. Теперь такие
структурные ошибки прерывают конвертацию. Приведённые выше статистические
результаты относятся к прежнему поведению.

Круговой инвариант относится к корректным записям, полностью представимым
в целевой схеме. JSON с ошибками валидации допускается в обратном преобразовании;
нарушения отражаются в отчёте без подмены значений.
