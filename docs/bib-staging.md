# БЗ в import.bib_records

Команда `documents stage` загружает готовые пакеты `prepare` в самостоятельную
`import.bib_records`. Она не выполняет загрузку в `public`/`public_26_10` и не создаёт
справочник `bib_ids`. UUID назначается непосредственно записи БЗ один раз при INSERT.
Существующие команды `load`, `ready` и `run` относятся к прежнему маршруту через
`public.documents`; для текущего цикла их запускать не следует.

Маршрут: `prepare/manifest.json` → проверка каждого NDJSON-пакета → временная COPY-таблица
→ классификация дублей → постоянная `bib_records` и журнал в одной транзакции.
Подготовленные записи повторно из DAT не разбираются. Для старой диагностики отказов
восстанавливаются только конкретные записи по известным смещениям, после проверки SHA DAT.

<a id="schema"></a>

## Состав и UUID

`initializeBibRecords` создаёт только таблицы в `import`. Если уже существует прежняя
`bib_records` без `accepted`, исполнение останавливается до изменения этой таблицы.

В `bib_records` есть все колонки `documents`: `id uuid`, `library_code varchar(6)`,
`system_number integer`, `leader varchar(25)`, `format varchar(5)`, `fields jsonb`,
`hidden boolean`, `meta jsonb`, `created_at timestamp`, `updated_at timestamp`.
`fields` — единственное сохранённое содержимое MARC. `meta` и `updated_at` пока NULL;
`hidden=false`, `created_at` назначается при загрузке. Нет `raw`, `payload`, `normalized`
или полной дополнительной JSON-копии записи. JSONB в TEMP существует только внутри COPY-транзакции.

Дополнительные колонки: `source_sha256`, `source_record_index` (с нуля), `byte_offset`,
`byte_length`, `accepted`, `rejection_code`, `rejection_reasons text[]`. Источник находится
через `bib_sources(sha256,path)`. Уникальны UUID, адрес `(source_sha256,byte_offset)` и
пара `(library_code,system_number)` среди `accepted=true`. В отличие от public, у номера
нет последовательности: берётся номер из исходника; NULL допускается только у отклонённой
записи с неизвестным номером. Принятый номер обязан быть положительным.

UUID будущие обработчики должны читать из `bib_records WHERE accepted`; перевод
потребителей связей с `bib_ids` и выгрузка в `public_26_10.documents` — следующие этапы,
а не действие этой команды. Текущая таблица предназначена для одного среза: новый DAT
с уже принятым библиотечным ключом считается повтором, существующая БЗ не перезаписывается.

`bib_record_batches` хранит SHA, число строк/принятых/отклонённых и время COMMIT каждого
пакета. `bib_record_runs` публикует итог исходника: processed, deleted, exported,
source_rejected, parsing_errors. В отличие от прежнего `bib_batches`, это типизированные
счётчики, без сохранения целой записи в JSON.

<a id="stage"></a>

## Запуск и продолжение

`stageBibRecords` принимает каталог prepare либо JSON-план с абсолютными каталогами:

```json
{"sources":["/work/reports/PREPARE_RSL01","/work/reports/PREPARE_RSL03"]}
```

```bash
docker exec marc-documents-worker node /app/dist/documents-worker-cli.js start \
  --stage stage --input /work/bib-stage-2026-10-26.json
docker exec marc-documents-worker node /app/dist/documents-worker-cli.js status
```

Worker создаёт task.id, `/work/reports/<id>.log` и `<id>.ndjson`. Задача независимо от
SSH последовательно вызывает `stageSource` для каждого исходника. Запуск допустим только
из опубликованного образа, OCI revision и digest которого соответствуют проверенному коду.
Обновлять занятый worker нельзя. Полный manifest и все каталоги проверяются перед соединением;
SHA каждого потока и количество строк проверяются перед COMMIT его пакета.

При повторе с новым отчётом `bib_record_batches` пропускает ранее зафиксированные пакеты
только с совпадающим SHA. Незаписанный пакет откатывается целиком, UUID прежних пакетов
сохраняются. Итог исходника публикуется лишь при совпадении суммы журналов и
`exported + rejected + parsingErrors`. Пустой DEL-only исходник также получает итог,
даже когда пакетов нет. Сбой останавливает цепочку, следующие библиотеки не начинаются.

`--dry-run` откатывает каждый пакет и не публикует итоги. Advisory-lock сериализует
загрузчики документов; `lock_timeout=60s`, `statement_timeout=30min`, проверка разрыва
соединения PostgreSQL каждые 5s, параллельные SQL worker отключены только в этой сессии.
Перед пакетом требуется не менее 2 GiB доступного места в рабочем каталоге.
Ошибки завершают CLI с кодом 1; соединение, транзакция и файл отчёта закрываются.

<a id="copy"></a>

## COPY и повторы

`stageRow` проверяет форму, идентификатор, отсутствие NUL и байтовый адрес. Временные
строки передаются через COPY CSV с TSV-разделителем; SQL NULL отличается от пустой строки.
Генератор `rows` читает `sourceLines` из gzip, преобразует запись в транспортную строку
и выдаёт COPY-потоку блок после накопления 64 KiB либо последний непустой остаток.
Граница блока не совпадает с границей записи; отдельная крупная запись может превысить 64 KiB.
Генератор возобновляется после потребления блока; gzip/файл могут иметь собственное чтение
наперед. Проверки SHA и числа записей завершаются до завершения COPY и COMMIT.

SQL нумерует вхождения номера внутри пакета, проверяет уже принятую пару в таблице и
помечает повтор `duplicate_identity`. Все вхождения сохраняются, первая принятая БЗ
сохраняет UUID; причины повтора находятся в `rejection_reasons`, а не в полном JSON источника.

Проверка существующей пары содержит `OFFSET 0`: это барьер оптимизации EXISTS,
сохраняющий корреляцию по системному номеру. Без него при неточной статистике планировщик
выбирал hash-subplan с чтением всей принятой библиотеки на каждом пакете: на сервере
время merge выросло с 2 до 16 секунд уже к 2,15 млн строк. Исправленный EXPLAIN
использует `Index Only Scan bib_records_identity` с обоими ключами — library_code
и system_number. Это защита от повторного полного обхода растущей таблицы;
семантика первого принятого вхождения и причин отказа не меняется.

<a id="rejections"></a>

## Отказы и DEL

`rejectionRows` связывает строку `validation` с последующей причиной по `recordIndex`.
`rejection_reasons` сохраняет отдельные сообщения правила/поля как элементы text[];
`rejection_code` различает `validation_rejected`, `invalid_identity`, `parse` и повторы.
MARC отказа, если он разобран, сохраняется в `fields`, `accepted=false`. У ошибки парсинга
поля пустые, leader/format пустые, причина и адрес сохранены; отсутствующая структура не выдумывается.

Новые diagnostics содержат `byteLength`. Для старых отказов Aleph функция `rejectedBytes`
начинает чтение со смещения и использует штатный splitter до первой полной записи
(максимум 16 MiB). Это точечное восстановление отказов; весь DAT заново не разбирается.
SHA DAT проверяется один раз перед восстановлением, stat — до и после, SHA diagnostics —
до и после. Несовпадение SHA, количества диагностик или recordId откатывает пакет отказов.
Для старого ISO без длины и для MARC с NUL команда останавливается с явной ошибкой;
автоматической замены или потери символа нет.

`prepare` пропускает DEL до записи пакетов. В существующем срезе 26.10 нет ни MARC,
ни индивидуальных адресов этих DEL в пакетах; поэтому они не превращаются в строки
`bib_records`. Их количество сохранено в `bib_record_runs.deleted`, отдельно от отказов.
В срезе ожидается 17 195 741 подготовленных БЗ и 34 отказа валидации; 1 454 207 DEL
учтены отдельно. RSL02 и RSL60 не имеют экспортированных БЗ.

## Наблюдение и проверки

Лог: `bib_source_start`, `bib_batch_committed`/`bib_batch_rolled_back`,
`bib_batch_skipped`, `bib_source_finished`, `bib_stage_waiting` каждые 10 секунд,
`bib_stage_finished`. Только committed означает фиксацию пакета; source_finished —
завершение исходника; stage_finished — завершение всех исходников плана. В отчёте
сохраняются количества пакетов и финальная отметка; failed task требует чтения лога.

Постоянный `<task-id>.ndjson` содержит UTC `time` у каждого события. Для всей загрузки,
библиотеки и пакета сохраняются `startedAt`, `finishedAt`, `elapsedMs`. Пакет дополнительно
содержит `copyMs` (чтение gzip, преобразование, SHA, COPY), `mergeMs` (ANALYZE, проверка
дублей и INSERT), `commitMs` (журнал БД и COMMIT/ROLLBACK), `recordsPerSecond`.
Начало и конец COPY/merge видны отдельными событиями; для восстановления отказов отдельно
замерены SHA исходного DAT и точечное восстановление. Пропущенный при повторе пакет
имеет событие skipped с длительностью проверки; он не выдаётся за новую загрузку.
stdout дублирует этот журнал в `.log`; сообщения ожидания каждые 10 секунд находятся
только в `.log`. Показатели COPY включают восстановление отказов, поэтому вложенные
замеры нельзя складывать как независимые этапы. Длительности — миллисекунды wall clock.

Интеграционные проверки: отдельная временная PostgreSQL, все колонки documents и MARC,
отсутствие public/bib_ids, стабильность UUID при повторе, dry-run, SHA и откат второго
пакета с продолжением, восстановление старого отказа по offset, дубли, DEL-only исходник.
Результат на малом наборе не является оценкой скорости загрузки полного среза.
