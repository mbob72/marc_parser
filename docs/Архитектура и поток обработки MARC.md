# Архитектура и поток обработки MARC

Документ описывает архитектуру проекта и оба потока преобразования MARC 21 /
ISO 2709 ↔ MARC-JSON/NDJSON. Детальные правила профиля РГБ и ссылки на PDF
приведены в [отдельном алгоритме](Алгоритм%20двусторонней%20конвертации%20MARC%20РГБ.md).

## Три части решения

1. **Потоковое ядро.** `convertMarcFile` формирует NDJSON из ISO 2709 или
   Aleph sequential, а `convertMarcJsonFile` по маркеру имени собирает ISO
   2709 или Aleph sequential из строк NDJSON.
2. **Инфраструктура выпуска.** Из CLI собираются standalone-бинарники
   для Linux, Windows и macOS. Матрица платформ задана в
   [release workflow](../.github/workflows/release.yml#L28-L65), а запуск Bun с
   `--compile` — в [скрипте сборки](../scripts/build-binary.mjs#L15-L28).
3. **Асинхронный сервис.** API принимает файл, сохраняет его и публикует
   задание в RabbitMQ
   ([загрузка и публикация](../src/api.ts#L59-L143)). Worker получает
   исходник из MinIO, выбирает поток по `direction`, а прямой контейнер — по
   сохранённому `input_format` (по умолчанию `aleph-sequential`), и сохраняет результат
   ([обработка задания](../src/worker.ts)). PostgreSQL хранит
   статус и статистику
   ([схема задания](../src/job-database.ts#L34-L52)), а API отдаёт статус и
   готовый результат
   ([GET-маршруты](../src/api.ts#L156-L195)).

Инфраструктура выпуска и асинхронный сервис выше даны обзорно. Дальнейшие
разделы подробно описывают потоковую конвертацию.

## Точка входа CLI

CLI запускает `main` с аргументами процесса
([точка входа](../src/cli.ts#L20-L24)). Затем `parseArgs` разбирает:

- входной и выходной пути;
- кодировку, по умолчанию `utf-8`;
- направление `--to-json` (по умолчанию) или `--to-iso`;
- флаг `--log` для подробного вывода валидации.

Разбор аргументов реализован в
[`parseArgs`](../src/cli.ts). После этого CLI создаёт логгер и вызывает
соответствующий файловый конвертер. Неперехваченная ошибка завершает CLI
с кодом `1`.

## Сборка потока конвертации

### ISO/Aleph sequential → NDJSON

`convertMarcFile` готовит имена файлов, создаёт зависимости и соединяет
этапы в `pipeline`:

```text
ReadStream
  -> автоопределение первых 10 байтов
  -> MarcRecordSplitter или AlephSequentialRecordSplitter
  -> MarcJsonTransform
       -> Iso2709MarcParser или AlephSequentialMarcParser
       -> MarcRecordValidator
       -> MarcJsonSerializer
  -> WriteStream временного JSON
  -> атомарное переименование
```

Каждая запись немедленно сериализуется как один компактный JSON-объект с `LF`.
Внешний JSON-массив не создаётся.

Зависимости `MarcJsonTransform` создаются в
[строках 52–57](../src/marc-file-converter.ts#L52-L57), а сам конвейер — в
[строках 67–72](../src/marc-file-converter.ts#L67-L72). Такая композиция не загружает
весь файл в память: в каждый момент обрабатывается чанк или одна MARC-запись.
Сервис использует тот же `convertMarcFile`, поэтому поддержка `.dat` не
дублируется в worker. В отличие от CLI, worker не применяет автоопределение:
API сохраняет multipart-поле `format` в `conversion_jobs.input_format`, а
worker передаёт его как `inputFormat`. Default сервиса — `aleph-sequential`;
для ISO 2709 клиент указывает `format=iso2709`.

Результат сначала пишется во временный файл, а после успешного завершения
переименовывается в итоговый
вместе с отдельным отчётом `*.validation-errors.ndjson`, если есть ошибки
валидации. Структурная ошибка прерывает поток; временные файлы удаляются.

### NDJSON → исходный контейнер

```text
ReadStream UTF-8 .iso.json или .aleph.json
  -> MarcJsonToIsoTransform (одна непустая строка = одна запись)
       -> JSON.parse + проверка модели
       -> MarcIsoSerializer или MarcAlephSequentialSerializer
  -> WriteStream временного .mrc/.dat
  -> атомарное переименование
```

Обратный поток находится в [`convertMarcJsonFile`](../src/marc-json-file-converter.ts).
Маркер `.iso.json` выбирает `MarcIsoSerializer`, `.aleph.json` —
`MarcAlephSequentialSerializer`; немаркированное имя отклоняется. Значения
MARC кодируются выбранной кодировкой через `iconv-lite`; сам NDJSON всегда
читается как UTF-8. Ошибка содержит номер строки и не публикует частичный файл.

## Разделение файла на MARC-записи

`MarcRecordSplitter` — алгоритмическое ядро потокового чтения. Он хранит
ещё не обработанные байты в `pending` и для каждого чанка вызывает
[`processChunk`](../src/marc-record-splitter.ts#L19-L28).

`processChunk` выполняет цикл:

1. добавляет новый чанк к `pending`
   ([строки 43–47](../src/marc-record-splitter.ts#L43-L47));
2. ждёт минимум пять байтов заголовка, из которых читает длину записи
   ([цикл](../src/marc-record-splitter.ts#L49-L54),
   [разбор длины](../src/marc-record-splitter.ts#L71-L90));
3. если данных пока мало, выходит и ждёт следующий чанк;
4. если запись накоплена целиком, вырезает её из начала `pending`;
5. передаёт запись в `MarcParserValidator`, который сверяет длину и проверяет
   завершающий байт `0x1D`
   ([проверки границ](../src/marc-parser-validator.ts#L12-L27));
6. вызывает `push`, чтобы передать полную запись дальше по конвейеру, и обновляет
   индекс и байтовое смещение
   ([извлечение и передача записи](../src/marc-record-splitter.ts#L56-L67)).

Если поток закончился, а в `pending` осталась неполная запись, `_flush` завершает
конвейер с ошибкой
([строки 30–41](../src/marc-record-splitter.ts#L30-L41)).

`AlephSequentialRecordSplitter` работает с формой
`9 цифр + TAB + поля с четырёхзначной байтовой длиной`. Он перемещается по
длинам полей и проверяет перевод строки только между полями. Это не позволяет
переводу строки внутри значения преждевременно завершить запись. После
выделения записи `AlephSequentialMarcParser` преобразует `LDR`, `FMT`,
индикаторы, `$$`-подполя и `^`-пробелы во внутреннее ISO-представление; далее
используются общий валидатор и сериализатор.

## Парсинг, валидация и сериализация одной записи

`MarcJsonTransform` получает от выбранного splitter целую MARC-запись. Метод `_transform`
делегирует её обработку в `convertRecord`
([строки 43–52](../src/marc-json-transform.ts#L43-L52)).
Каждый вызов выдаёт законченную строку NDJSON. Пустой вход не требует
специального закрывающего маркера и даёт пустой файл.

### Успешный путь

1. `parser.parse` превращает байты в структуру `MarcRecord`
   ([вызов парсера](../src/marc-json-transform.ts#L68-L76)).
2. `validator.validate` проверяет распарсенную запись, после чего результат
   передаётся логгеру
   ([валидация и логирование](../src/marc-json-transform.ts#L91-L94)).
3. `serializer.serialize` преобразует запись и ошибки валидации в JSON-объект
   ([сериализация](../src/marc-json-transform.ts#L95-L99)).
4. Статистика отдельно учитывает корректные записи и записи с ошибками
   валидации
   ([счётчики](../src/marc-json-transform.ts#L100-L105)).
5. `finishRecord` добавляет `LF`, обновляет индекс и байтовое смещение.

### Ошибка парсинга

Исключение из `parser.parse` логируется и прерывает обработку файла.
Частичный JSON не публикуется.

### Важное различие типов ошибок

Структурные ошибки длин, смещений и разделителей не позволяют надёжно
разобрать запись и приводят к исключению. Ошибки валидации уже разобранных
значений сохраняются в отчёте; сериализатор сохраняет исходные значения,
а обработка следующих записей продолжается.

## Ядро парсера ISO 2709

`Iso2709MarcParser.parse` собирает `MarcRecord` из трёх основных составляющих:

1. `Leader`;
2. `Directory`;
3. поля записи.

Верхнеуровневая сборка находится в
[`Iso2709MarcParser.parse`](../src/marc-parser.ts#L22-L45): сначала читается
24-байтовый `Leader`, из него извлекается `baseAddressOfData`, затем разбираются
`Directory` и поля. Результирующие типы описаны в
[`marc-record.ts`](../src/marc-record.ts#L1-L82).

Детальный порядок разбора `Leader`, `Directory`, контрольных и обычных
полей инкапсулирован во внутренних функциях `marc-parser.ts` и не влияет на
верхнеуровневую композицию конвейера.

## Валидатор

`MarcRecordValidator.validate` создаёт список ошибок и последовательно проверяет
длину записи, `Leader`, `Directory` и поля
([точка входа валидатора](../src/marc-validator.ts#L43-L57)).

Ошибки кодифицированы: каждая содержит `rule`, текст и при необходимости контекст
поля, индикатора или подполя
([типы правил и ошибок](../src/marc-validator.ts#L7-L30)). Конкретные проверки
реализованы в [`validateRecordLength`](../src/marc-validator.ts#L59-L69),
[`validateLeader`](../src/marc-validator.ts#L71-L88),
[`validateDirectory`](../src/marc-validator.ts#L90-L104) и
[`validateFields`](../src/marc-validator.ts#L106-L176).

## Итоговая модель ошибок

| Ситуация | Поведение | Результат |
| --- | --- | --- |
| Невозможно выделить целую запись или нарушены её границы | Выбранный splitter / framing validator завершают `pipeline` с ошибкой | Выходной файл не публикуется |
| Отдельная запись не парсится | Исключение прерывает поток | Частичный результат не публикуется |
| Запись разобрана, но не проходит валидацию | Ошибки записываются в отдельный отчёт, значения сохраняются | Обработка продолжается, ошибки учитываются в статистике |
