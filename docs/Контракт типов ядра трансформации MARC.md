# Контракт типов ядра трансформации MARC

Документ фиксирует публичный TypeScript-контракт между ядром
двусторонней трансформации MARC и внешней, в том числе устаревшей,
утилитой. Контракт не зависит от Node.js, файлового API, HTTP API,
очереди заданий или внутренних классов конвертера.

Машиночитаемый источник типов:
[`contracts/marc-transform-contract.ts`](../contracts/marc-transform-contract.ts).
Текущая версия контракта — `1.0.0`.

## Как использовать в старой утилите

1. Скопировать `marc-transform-contract.ts` в исходный код утилиты.
2. Импортировать нужные типы через `import type`. Константы и функции-
   предикаты импортируются как обычные значения.
3. Проверять JSON в runtime перед присваиванием
   `SerializableMarcJsonRecord`: TypeScript не проверяет данные, прочитанные
   из файла или полученные по сети.

Файл не требует зависимостей. Он не импортирует `Buffer` и поэтом пригоден
как для Node.js, так и для браузерного TypeScript-проекта.

## Границы контракта

Контракт описывает:

- контейнеры `iso2709` и `aleph-sequential`;
- MARC-JSON-запись, её поля и подполя;
- различие между результатом прямого преобразования и допустимым входом
  обратного преобразования;
- опции ядра, контекст записи, ошибки валидации и статистику.

В контракт не входят внутреннее байтовое представление `MarcRecord`,
реализация Node.js Streams, имена файлов и API сервиса.

## Направления трансформации

### ISO 2709 / Aleph sequential → MARC-JSON

Результат одной записи имеет тип `ParsedMarcJsonRecord`.
В нём допустим `"<unrecognized>"`: прямая трансформация не прерывает весь
файл из-за локальной ошибки записи.

Если запись не удалось разобрать, ядро выдаёт:

```json
{"leader":"<unrecognized>","format":"<unrecognized>","fields":[]}
```

В Aleph sequential верхнеуровневое `recordId` содержит первую девятизначную
колонку Z00. Для ISO 2709 `recordId` не формируется.

### MARC-JSON → ISO 2709 / Aleph sequential

Структурно допустимая запись имеет тип `SerializableMarcJsonRecord`.
Для явного контейнера лучше использовать более узкий тип:

- `IsoMarcJsonRecord` — для ISO 2709;
- `AlephMarcJsonRecord` — для Aleph sequential, с обязательным
  девятизначным `recordId`.

Для совместимости ядро также может получить Aleph `recordId` из числового
контрольного поля `001` длиной от одной до девяти цифр, дополнив его
нулями слева. Это fallback режима совместимости; новый код должен передавать
`recordId` явно.

## Поля MARC-JSON

### Запись

| Свойство | TypeScript-тип | Runtime-ограничение |
| --- | --- | --- |
| `leader` | `string` | Ровно 24 ASCII-символа; позиции 18 и 19 ограничены профилем РГБ. |
| `format` | `MarcJsonFormat` | Один из `AN`, `AU`, `BK`, `CF`, `CR`, `MP`, `MU`, `MX`, `SE`, `VM`. |
| `fields` | `readonly MarcJsonField[]` | Массив без служебного `FMT`; он перенесён в `format`. |
| `recordId` | `string \| undefined` | Ровно девять цифр; служебное свойство Aleph sequential. |

Leader/18 не допускает `c` и `n`, Leader/19 не допускает `a`, `b` и `c`.

### Контрольное поле

```ts
interface MarcJsonControlField {
  readonly code: string;
  readonly value: string;
}
```

Ограничения:

- `code` имеет вид `00X`, где `X` — допустимый символ тега;
- свойства `ind1`, `ind2` и `subfields` отсутствуют;
- `FMT` не передаётся в `fields`.

### Поле данных

```ts
interface MarcJsonDataField {
  readonly code: string;
  readonly ind1: string;
  readonly ind2: string;
  readonly subfields: readonly MarcJsonSubfield[];
}
```

Ограничения:

- `code` — три цифры или три латинские буквы, но не `00X` и не `FMT`;
- `ind1` и `ind2` — по одному символу из латинской строчной буквы, цифры,
  пробела или `#`; при записи `#` преобразуется в ASCII-пробел;
- `subfields` — непустой массив;
- свойство `value` отсутствует.

Код подполя состоит из одной строчной латинской буквы или цифры.

## NDJSON-контейнер

При файловом обмене MARC-JSON передаётся как NDJSON:

- одна запись — один компактный JSON-объект на строке;
- после каждого объекта, включая последний, записывается `LF`;
- внешнего JSON-массива и запятых между объектами нет;
- пустые строки при обратном чтении пропускаются;
- pretty-printed JSON и JSON-массив не являются частью контракта.

Для обратного файлового преобразования целевой контейнер определяется по
маркеру имени:

| Имя JSON | Целевой контейнер |
| --- | --- |
| `*.iso.json`, `*.iso.ndjson` | ISO 2709 |
| `*.aleph.json`, `*.aleph.ndjson` | Aleph sequential |

## Ошибки и статистика

`MarcValidationError` фиксирует код правила, текст ошибки и, если ошибка
локализована, индексы поля, индикатора или подполя. Все индексы нулевые.

`MarcProcessingStatistics` описывает счётчики завершённой обработки. `inputBytes` — число
обработанных байтов, а не длина текста в Unicode-символах.

## Версионирование

Контракт версионируется по SemVer в `MARC_TRANSFORM_CONTRACT_VERSION`:

- `PATCH` — уточнения документации без изменения допустимых данных;
- `MINOR` — обратно совместимое расширение;
- `MAJOR` — несовместимое изменение структуры или семантики.

Полный алгоритм, включая байтовые правила ISO 2709 и Aleph sequential,
описан в [документе по двусторонней конвертации](./Алгоритм%20двусторонней%20конвертации%20MARC%20РГБ.md).
