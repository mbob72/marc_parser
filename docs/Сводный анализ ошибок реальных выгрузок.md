# Сводный анализ ошибок реальных выгрузок РГБ

<!-- vf-g5-deprecated:start -->
**VF-G5 — deprecated с 22.09.2026.** В новых проверках недопустимый код подполя даёт только SF-G4. VF-G5 в прежних выгрузках сохранён как исторический дубликат SF-G4; старые количества и реестры не пересчитывались. Упоминания пары ниже описывают поведение на момент соответствующего прогона.
<!-- vf-g5-deprecated:end -->

Документ обобщает полную проверку файлов `rsl06_z00.dat`,
`rsl07_z00.dat` и `rsl10_z00.dat`. Полный построчный реестр с Z00 ID и
байтовыми смещениями находится в
[отчёте по реальным выгрузкам](%D0%9E%D1%88%D0%B8%D0%B1%D0%BA%D0%B8%20%D0%B2%D0%B0%D0%BB%D0%B8%D0%B4%D0%B0%D1%86%D0%B8%D0%B8%20%D1%80%D0%B5%D0%B0%D0%BB%D1%8C%D0%BD%D1%8B%D1%85%20%D0%B2%D1%8B%D0%B3%D1%80%D1%83%D0%B7%D0%BE%D0%BA.md).

## Итоговые числа

| Показатель | Количество |
| --- | ---: |
| Обработано записей | 900 831 |
| Записей с ошибками валидации | 143 |
| Срабатываний правил валидации | 151 |
| Первичных дефектов после объединения каскадов | 143 |
| Записей с ошибками парсинга | 6 |
| Всего проблемных логических записей | 149 |

Валидация запускается только после успешного парсинга. Поэтому шесть
ошибок парсинга не входят ни в 143 записи, ни в 151 срабатывание.

## 1. Ошибки, не нарушающие структуру записи

Эти 143 записи успешно преобразованы во внутреннюю MARC-модель. Их
нарушения должны считаться **предупреждениями**, а не причиной удаления
исходного значения из JSON.

| Первичная причина | Записей | Срабатывающие правила |
| --- | ---: | --- |
| Код Leader/19 запрещён профилем РГБ | 110 | `LD-02` |
| Нет кода подполя | 8 | `DF-G3` |
| Недопустимый индикатор | 15 | `IN-G3`; один каскад `DF-G2` + `VF-G5` + `SF-G4` |
| Повреждён тег поля | 5 | `DR-E2`; один каскад `DR-E2` + `DF-G3` |
| Недопустим код подполя | 5 | `VF-G5` + `SF-G4` |
| **Итого** | **143** | **151 срабатывание** |

### 1.1. Коды Leader/19 — 110 записей

- `rsl06_z00.dat`: 106 записей, из них 43 с кодом `a` и 63 с `c`;
- `rsl07_z00.dat`: 4 записи, по 2 с кодами `a` и `c`.

Коды `a`, `b`, `c` имеют семантику в MARC 21, но не допущены в Leader/19
профиля РГБ. Это профильный конфликт, а не ошибка чтения Leader.

Консервативная проверка семантики дала:

| Оценка | Записей |
| --- | ---: |
| Код семантически обоснован | 74 |
| Код, вероятно, выбран неверно | 20 |
| Неоднозначно по метаданным | 12 |
| Нельзя оценить: удалённая запись | 4 |

Для `rsl06` отдельно выделены
[27 точных двухзаписных серий](rsl06-ld02-error-pairs.md).

### 1.2. Отсутствует код подполя — 8 записей

| Поле | Записей | Характер дефекта |
| --- | ---: | --- |
| `DEL` | 3 | Локальные данные удаления записаны без `$$a` |
| `410` | 2 | Текст следует сразу за индикаторами |
| `110`, `490`, `678` | по 1 | Тот же дефект |

Это восемь самостоятельных `DF-G3`. Девятое срабатывание `DF-G3` относится
к повреждённому тегу `@08` и учтено ниже как каскад.

### 1.3. Недопустимые индикаторы — 15 записей

- `0x01`: 12 записей;
- `0x1C`: 1 запись;
- `;`: 1 запись;
- `0x1F`: 1 запись с каскадом трёх правил.

В Z00 `000212087` байт `0x1F` попал в позицию первого индикатора поля `667`.
Он одновременно является разделителем подполя, поэтому один байт привёл к:

1. `DF-G2`: парсер увидел ноль индикаторов;
2. `VF-G5`: пробел стал недопустимым кодом подполя;
3. `SF-G4`: та же проверка дополнительно зарегистрировала второй код ошибки.

### 1.4. Повреждённые теги — 5 записей

| Тег | Записей | Комментарий |
| --- | ---: | --- |
| `" 10"` | 2 | Первая цифра утрачена; точный тег неоднозначен |
| `"@70"` | 1 | По содержанию, вероятно, `670` |
| `"\u001110"` | 1 | По содержанию, вероятно, `410` |
| `"@08"` | 1 | Практически однозначно `008` |

В Z00 `000239114` ошибка `@08` вместо `008` привела и к `DR-E2`, и к `DF-G3`:
из-за тега поле не было распознано как контрольное и было дополнительно
проверено как поле данных без подполей.

### 1.5. Недопустимые коды подполей — 5 записей

| Z00 ID | Поле | Код |
| --- | --- | --- |
| `000049344` | `040` | `D` |
| `000230421` | `667` | `B` |
| `000232888` | `410` | `0x1E` |
| `000240521` | `410` | `P` |
| `000246018` | `411` | `R` |

В этом историческом прогоне каждый дефект давал пару `VF-G5` + `SF-G4`:
одна проверка кода подполя добавляла два сообщения. Это пять, а не десять
первичных ошибок.

### 1.6. Почему 143 записи дают 151 срабатывание

Несколько правил сработали в семи записях:

- пять прямых ошибок кода подполя: по два срабатывания;
- Z00 `000212087`: три срабатывания из-за одного `0x1F`;
- Z00 `000239114`: два срабатывания из-за одного тега `@08`.

Эти семь записей дают 15 срабатываний вместо семи, то есть восемь
дополнительных срабатываний: `143 + 8 = 151`.

## 2. Ошибки парсинга одной записи — 6 записей

Все шесть записей корректно выделяются из Aleph-потока: длины полей и границы
записей читаются. Ошибка возникает при попытке построить MARC-модель. Они
не повреждают следующие записи, но фатальны для текущей записи.

| Причина | Записей | Восстановимость |
| --- | ---: | --- |
| Кириллическая `т` в Leader/17 даёт 25 байт вместо 24 | 4 | Однозначно исправляется |
| Поле `LDR` отсутствует | 1 | Исходную MARC-запись достоверно восстановить нельзя |
| В записи два разных `LDR` | 1 | Выбор второго `LDR` обоснован, но требует также замены `FMT` |

### 2.1. Четыре Leader длиной 25 байт

| Z00 ID | Исходный Leader |
| --- | --- |
| `000015451` | `00358nz^^a2200169т^^4500` |
| `000018979` | `00795nz^^a2200193т^^4500` |
| `000022352` | `00430nz^^a2200157т^^4500` |
| `000027433` | `00431nz^^a2200169т^^4500` |

Кириллическая `т` кодируется в UTF-8 двумя байтами `D1 82`. В соседних
авторитетных записях в Leader/17 стоит ASCII `n`. Однозначное исправление:

```text
т → n
длина Aleph-поля 0031 → 0030
```

После исправления все четыре записи парсятся, определяются как `AU` и
проходят валидатор без ошибок.

### 2.2. Запись без `LDR`

`rsl07_z00.dat`, номер 518569, Z00 `000525445`, смещение 172839158.
В записи есть только:

```text
CAT  $$c20230608$$lRSL07$$h1138
DEL            20230608
```

Нет `FMT`, `LDR`, `001` и содержательных MARC-полей. Это похоже на неполную
запись удаления. Синтез обычного Leader был бы выдумыванием метаданных.

### 2.3. Запись с двумя `LDR`

`rsl10_z00.dat`, номер 129838, Z00 `000167015`, смещение 64268293:

```text
FMT  BK
LDR  ^^^^^nam^a22^^^^^^i^4500
LDR  00744nz^^a2200181n^^4500
111  $$a"50 years Department of zoology, Plovdiv university",
     international conference on zoology$$d2012$$cHissar
670  $$aГАК РГБ
```

Первый Leader описывает библиографическую монографию, второй — авторитетную
запись. Поля `111`, `670` и структура `008` согласуются со вторым Leader. Обоснованная
коррекция:

1. удалить первый `LDR`;
2. оставить второй `LDR`;
3. заменить `FMT BK` на `FMT AU`.

После этой коррекции запись также проходит валидатор без ошибок.

## 3. Влияние текущей реализации

Сейчас валидационные ошибки заменяют повреждённые части на `"<unrecognized>"`,
а ошибка парсинга заменяет на такую заглушку всю запись. Обратный
конвертер отклоняет `"<unrecognized>"`. Поэтому ни один из 149 проблемных
случаев не имеет гарантированного двустороннего преобразования.

Предлагаемое изменение описано отдельно:
[обработка ошибок без потери данных](%D0%9F%D1%80%D0%B5%D0%B4%D0%BB%D0%BE%D0%B6%D0%B5%D0%BD%D0%B8%D0%B5%20%D0%BF%D0%BE%20%D0%BE%D0%B1%D1%80%D0%B0%D0%B1%D0%BE%D1%82%D0%BA%D0%B5%20%D0%BE%D1%88%D0%B8%D0%B1%D0%BE%D0%BA%20%D0%B1%D0%B5%D0%B7%20%D0%BF%D0%BE%D1%82%D0%B5%D1%80%D0%B8%20%D0%B4%D0%B0%D0%BD%D0%BD%D1%8B%D1%85.md).
