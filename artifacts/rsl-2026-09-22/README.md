# Повторный анализ РГБ, 22.09.2026

Обрабатываются только `rsl01`, `rsl03`, `rsl06`, `rsl07`, `rsl10`, `rsl11`.
`rsl02` исключена. Режим `errors-only`: парсинг и валидация без сериализации
MARC-JSON. Исторические артефакты от 17.09.2026 не изменяются.

Текущее состояние — [run-manifest.json](run-manifest.json). Значение
`stage: complete` означает, что все шесть файлов пройдены, контрольные суммы
проверены и итоговый отчёт сформирован. Наличие отдельных файлов сводок ещё
не означает завершение всего набора.

После завершения:

- [Общий отчёт](../../docs/RSL-validation-2026-09-22.md).
- `*.errors-only.errors.ndjson` — ошибки с исходными ID и смещениями записей.
- `*.errors-only.summary.json` — статистика, SHA-256 DAT и длительность прохода.
- `by-type/*.tsv` — полный реестр каждого типа с адресами проблемных полей.
- `records/` — исходные байты и текстовые представления примеров для Sublime.
- `by-type-manifest.json` — сверенные количества, сравнение тех же шести баз
  с историческим прогоном, SHA-256 генератора отчёта.

`recordIndex`, `fieldIndex`, `subfieldIndex`, `indicatorIndex`, `byteOffset`
начинаются с нуля. `fieldIndex` относится к модели после фильтрации служебных
полей, включая внутренний FMT. Поля `sourceFieldNumber`, `fieldByteOffset`
и `problemByteOffset` в TSV помогают найти дефект в исходном DAT.

Зафиксированы Git revision и SHA-256 кода на начало запуска. `implementation.patch`
содержит изменения аудитора относительно этого коммита; `audit-rsl.ts.txt`,
`run-rsl-errors-audit.py.txt` и `report-rsl-errors.py.txt` сохраняют использованные
скрипты. Генератор отчёта проверяет совпадение количества ошибок NDJSON со сводками.
Архивы, восстановленные с исходного сервера, сверяются с SHA-256 LFS-указателей;
DAT сверяются с SHA-256 и количеством записей исторического прогона.
